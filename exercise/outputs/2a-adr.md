# ADR-0002: ใช้ durable event เพื่อแยกงานหลังการสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุผู้มีอำนาจตัดสินใจ

## Context and problem

- **Evidenced — requirement จากผู้ใช้ ข้อ 1–3:** หลังสั่งซื้อ Online Boutique ต้องส่งอีเมลยืนยันผ่าน MailFast ซึ่งแทนที่ mock logic ของ emailservice, ให้คะแนนผ่าน loyaltyservice ที่ต้องสร้างใหม่ และบันทึก event “order placed” สำหรับทีมการตลาด
- **Evidenced — requirement จากผู้ใช้ ย่อหน้าสุดท้าย:** ทีมการตลาดคาดว่าจะเพิ่ม SMS, fraud scoring และการปรับปรุง recommendations ในปีหน้า
- ไม่มีไฟล์ context สำหรับยืนยันสถาปัตยกรรมปัจจุบัน: **Not evidenced in the provided files** จึงไม่สรุปว่าปัจจุบันใครเรียกใคร ใช้ protocol ใด หรือมีฐานข้อมูลและ message broker อยู่แล้ว
- ต้องตัดสินใจว่าจะเชื่อมงานหลังสั่งซื้ออย่างไร ให้เพิ่มงานใหม่ได้ และจัดการความล้มเหลวของแต่ละงานได้อย่างชัดเจน
- **Assumption:** งานทั้งสามยอมให้สำเร็จภายหลังการตอบรับคำสั่งซื้อได้ และความล้มเหลวของงานเหล่านี้ไม่ย้อนยกเลิกคำสั่งซื้อ ต้องยืนยันกับผู้เกี่ยวข้องก่อนรับรอง ADR

## Decision drivers

เรียงตามลำดับความสำคัญที่เสนอเพื่อพิจารณา ไม่ใช่ลำดับที่ผู้ใช้ยืนยันแล้ว

- ความครบถ้วนของงานและการกู้คืนเมื่อส่งต่อไม่สำเร็จ (reliability)
- ความสะดวกในการเพิ่ม post-order action โดยลดการแก้ส่วนวางคำสั่งซื้อ (modifiability)
- การแยกผลกระทบจาก MailFast และบริการปลายทางที่ล่ม (availability)
- เวลาตอบกลับเมื่อสั่งซื้อและเวลารอให้งานแต่ละชนิดเสร็จ (performance)
- ต้นทุนโครงสร้างพื้นฐาน การดูแล และการติดตามงาน (cost, operability)

## Considered options

1. เรียกงานทั้งสามโดยตรงแบบ synchronous จากส่วนวางคำสั่งซื้อ
2. ส่งงานให้ตัวประสานงานแบบ asynchronous ซึ่งควบคุม workflow และเรียกแต่ละปลายทาง
3. เผยแพร่ durable OrderPlaced event ผ่าน message broker ให้ consumer ของแต่ละงานทำงานอิสระ

### Pros and cons of the options

ข้อดีและข้อเสียต่อไปนี้เป็นการประเมินแนวทางที่เสนอ ไม่ใช่ผลวัดของระบบปัจจุบัน

| Option | Pros | Cons |
|---|---|---|
| 1 — เรียกโดยตรง | เริ่มต้นได้ด้วยกลไกน้อย; ทราบผลตอบรับของแต่ละงานใน request เดียว | latency ของปลายทางกระทบการตอบกลับ; ต้องกำหนดการจัดการ partial failure; เพิ่มงานแล้วต้องแก้ส่วนวางคำสั่งซื้อ |
| 2 — ตัวประสานงาน | ควบคุมลำดับและติดตามสถานะรวมได้ชัด; แยกการตอบรับคำสั่งซื้อออกจากการทำงานปลายทางได้ | ต้องดูแลสถานะ workflow และ retry; เพิ่มงานต้องแก้ workflow ส่วนกลาง; ตัวประสานงานเป็นจุดรวมของความซับซ้อน |
| 3 — กระจาย event | เพิ่ม consumer ใหม่ได้โดยไม่เพิ่มการเรียกจากผู้ผลิต event หากข้อมูลในสัญญาเพียงพอ; แยก retry และการขยายกำลังของแต่ละงาน | ต้องมี durable messaging และการป้องกันผลซ้ำ; ผลสำเร็จเกิดต่างเวลากัน; การติดตามงานข้าม consumer ซับซ้อนขึ้น |

## Decision

เสนอเลือก **ตัวเลือก 3** เพราะความต้องการเพิ่มงานหลังสั่งซื้อสนับสนุนการแยก consumer ตามหน้าที่ และงานปัจจุบันไม่ได้ระบุว่าต้องทำตามลำดับ ทั้งนี้ต้องยืนยันสมมติฐานเรื่อง asynchronous completion ข้างต้น

รายละเอียดทั้งหมดในส่วนนี้เป็น **ข้อเสนอใหม่** ไม่ใช่ข้อเท็จจริงจากโค้ด:

- ให้ส่วนที่รับผิดชอบการยืนยันคำสั่งซื้อผลิต OrderPlaced หลังถึงจุดที่ธุรกิจถือว่าสั่งซื้อสำเร็จ ต้องตกลงนิยามจุดนี้ก่อนออกแบบรายละเอียด
- ทำให้การยืนยันคำสั่งซื้อและความตั้งใจส่ง event กู้คืนได้โดยไม่เกิดช่องว่างที่คำสั่งซื้อสำเร็จแต่ event สูญหาย ใช้ transactional outbox หากมีที่เก็บสถานะซึ่งบันทึกทั้งสองอย่างใน transaction เดียวกันได้ แล้วให้ publisher ส่งซ้ำจน broker ยืนยัน หากทำไม่ได้ ต้องออกแบบกลไกที่ให้หลักประกันเทียบเท่าก่อนนำไปใช้; ยังไม่ระบุฐานข้อมูลหรือผลิตภัณฑ์ broker
- ใช้ broker ที่เก็บข้อความแบบ durable และให้แต่ละ consumer มี subscription/queue ของตนเอง เพื่อให้ทุกงานได้รับ event เดียวกัน ใช้การส่งมอบแบบ at-least-once และรับทราบข้อความหลังจัดเก็บผลสำเร็จที่จำเป็นแล้ว
- กำหนดสัญญา event ขั้นต้นให้มี eventId, eventType, schemaVersion, orderId และ occurredAt พร้อม correlation สำหรับติดตามงาน ข้อมูลเพิ่มเติมและแหล่งอ่านข้อมูลคำสั่งซื้อต้องตกลงตามสัญญาของแต่ละ consumer; จำกัดข้อมูลส่วนบุคคลและไม่บรรจุข้อมูลชำระเงินที่ไม่จำเป็น
- ปรับ emailservice ให้ consumer/adapter เรียก MailFast แทน mock logic โดยแยก credentials และ mapping ของผู้ให้บริการออกจากผู้ผลิต event; protocol และวิธียืนยันการส่งต้องตรวจจากสัญญา MailFast ภายหลัง
- สร้าง loyaltyservice ให้รับ event และบันทึกการให้คะแนนตามกฎที่ธุรกิจจะกำหนด ใช้ orderId ร่วมกับชนิดรายการคะแนนเป็นกุญแจกันซ้ำ และบันทึกกุญแจกับผลคะแนนอย่าง atomic
- เพิ่ม analytics consumer เพื่อบันทึก “order placed” ให้ทีมการตลาด โดยกันซ้ำด้วย eventId และกำหนดนิยามการนับให้ชัดเจน ไม่อ้างว่ามี analytics platform อยู่แล้ว
- แต่ละ consumer ต้อง retry โดยมี backoff และขอบเขตที่กำหนดได้ แยกข้อผิดพลาดถาวรไปยัง dead-letter queue พร้อม alert และ replay ที่ตรวจสอบได้; ยังไม่กำหนดค่าจำนวนครั้งหรือระยะเวลา
- สำหรับ MailFast ใช้ idempotency key ที่คงเดิมสำหรับงานอีเมลเดียวกัน หากผู้ให้บริการรองรับ ต้องยืนยันความสามารถนี้ก่อนอ้างว่าป้องกันอีเมลซ้ำได้ หากส่งสำเร็จแล้วขาดการตอบกลับ ให้ตรวจสถานะหรือกระทบยอดตาม API ที่รองรับ; หากไม่มีความสามารถดังกล่าว ยังคงมีความเสี่ยงอีเมลซ้ำและต้องตกลงแนวทางจัดการ
- เพิ่ม SMS หรือ recommendations consumer ในอนาคตได้เมื่อสัญญา event รองรับ โดยไม่ต้องเพิ่มขั้นตอนเรียกปลายทางในส่วนวางคำสั่งซื้อ ส่วน fraud scoring ต้องพิจารณาใหม่หากผลของมันต้องใช้อนุมัติก่อนยืนยันคำสั่งซื้อ

## Consequences

- **Positive:** เพิ่ม consumer ของ post-order action ได้โดยลดการแก้ผู้ผลิต event ภายใต้สัญญาที่เข้ากันได้ (quality attribute: modifiability)
- **Positive:** เมื่อ MailFast หรือ consumer หยุดทำงาน งานสามารถค้างรอและกลับมาทำต่อได้ภายในขีดจำกัดการเก็บข้อความที่กำหนด (quality attribute: availability, reliability)
- **Positive:** การตอบรับคำสั่งซื้อไม่ต้องรอผลของทุก consumer ตามสมมติฐานที่เสนอ แต่ยังมีต้นทุนการบันทึกงานอย่าง durable (quality attribute: performance)
- **Negative:** ผู้ใช้และการตลาดอาจเห็นอีเมล คะแนน และ analytics พร้อมใช้คนละเวลา จึงต้องกำหนดเวลารอที่ยอมรับได้ (quality attribute: consistency, usability)
- **Negative:** ต้องดูแล broker, publisher, consumer, dead-letter queue และการติดตามงาน เพิ่มภาระและค่าใช้จ่ายที่ยังประเมินเป็นตัวเลขไม่ได้ (quality attribute: cost, operability)
- **Risks and mitigations:** event หายระหว่างยืนยันคำสั่งซื้อกับเผยแพร่ → ใช้ outbox หรือกลไกที่ให้หลักประกันเทียบเท่า พร้อมกระทบยอดคำสั่งซื้อกับงานที่ส่ง (quality attribute: reliability)
- **Risks and mitigations:** redelivery หรือ crash หลังทำผลข้างเคียงแล้ว → ใช้กุญแจกันซ้ำและบันทึกแบบ atomic ในระบบที่ควบคุมได้; การส่งอีเมลขึ้นกับความสามารถของ MailFast และยังไม่รับประกัน exactly-once (quality attribute: correctness)
- **Risks and mitigations:** backlog, event ที่ประมวลผลไม่ได้ และ schema ที่เปลี่ยน → ติดตามอายุงานค้าง, alert, replay และทดสอบความเข้ากันได้ของ schema; ต้องกำหนด retention ให้ครอบคลุมช่วงกู้คืนที่ตกลงกัน (quality attribute: reliability, operability, modifiability)
- **Risks and mitigations:** ข้อมูลลูกค้ากระจายไปยัง consumer มากเกินจำเป็น → จำกัด payload และสิทธิ์เข้าถึง subscription รวมถึงกำหนด retention ของข้อมูล (quality attribute: security, privacy)

## Validation

เป็นแผนตรวจสอบหลังพัฒนา ยังไม่มีผลทดสอบหรือค่าประสิทธิภาพจากไฟล์ context

- ทดสอบคำสั่งซื้อที่ยืนยันแล้วหนึ่งรายการ: มี event ที่ส่งต่อได้, emailservice เรียก MailFast แทน mock, loyaltyservice ให้คะแนนตามกฎที่ตกลง และ analytics บันทึก event ตามนิยามการนับ
- จำลอง crash ระหว่างการบันทึกคำสั่งซื้อกับการเผยแพร่ event แล้วกู้คืน: ต้องไม่มีคำสั่งซื้อที่สำเร็จแต่ไม่มีงานส่งต่อ หากเกิด rollback ต้องไม่เผยแพร่ event ของคำสั่งซื้อที่ไม่สำเร็จ
- ส่ง event เดิมซ้ำและจำลอง consumer crash หลังเกิดผลข้างเคียง: คะแนนและ analytics ต้องไม่ซ้ำ; ตรวจผลอีเมลตามสัญญา idempotency/การตรวจสถานะของ MailFast และบันทึกข้อจำกัดที่ยังเหลือ
- จำลอง MailFast ล่มและ consumer บางตัวหยุดทำงาน: ตรวจการค้างรอ การกู้คืน retry, dead-letter queue, alert และ replay โดยงานอื่นยังดำเนินต่อได้
- วัดเวลาตอบรับคำสั่งซื้อ เวลาจาก event ถึงงานสำเร็จ อายุงานค้าง อัตรางานล้มเหลว และรายการที่กระทบยอดไม่ตรง แล้วเทียบ SLO ที่ผู้เกี่ยวข้องจะกำหนด
- ทดลองเพิ่ม consumer จำลองอีกหนึ่งชนิดและทดสอบ schema compatibility เพื่อยืนยันว่าไม่ต้องเพิ่มการเรียกปลายทางในผู้ผลิต event เมื่อสัญญาเดิมเพียงพอ

## Open questions

- ใครเป็นผู้ตัดสินใจและรับผิดชอบการดูแลแต่ละ consumer รวมถึง broker?
- จุดใดถือว่าสั่งซื้อสำเร็จ และบริการใดเป็นเจ้าของการยืนยัน? มีที่เก็บสถานะและ transaction ที่รองรับ outbox หรือกลไกเทียบเท่าหรือไม่?
- ธุรกิจยอมรับ asynchronous completion ของอีเมล คะแนน และ analytics หรือไม่? หากงานล้มเหลวถาวรต้องชดเชยหรือแจ้งใคร?
- SLO, ปริมาณคำสั่งซื้อ, ระยะ outage ที่ต้องทน, retention, ขอบเขต retry และงบประมาณเป็นเท่าใด?
- MailFast ใช้ protocol, authentication, rate limit, timeout, idempotency และ API ตรวจสถานะแบบใด? “ส่งสำเร็จ” หมายถึงผู้ให้บริการรับคำขอหรืออีเมลถึงปลายทาง?
- ระบุตัวสมาชิก loyalty อย่างไร ใช้กฎคำนวณคะแนนใด และจัดการการยกเลิก/คืนเงินอย่างไร?
- ทีมการตลาดต้องการข้อมูลใด ปลายทาง analytics คืออะไร และนิยาม event “order placed” กับการกันซ้ำเป็นอย่างไร?
- consumer จะได้รับหรืออ่านข้อมูลอีเมลและรายการคำสั่งซื้อจากที่ใด? ต้องปฏิบัติตามข้อจำกัดด้าน privacy และ retention อะไรบ้าง?
- งานอนาคตต้องมีลำดับหรือเงื่อนไขร่วมกันหรือไม่ โดยเฉพาะ fraud scoring ต้องเกิดก่อนอนุมัติคำสั่งซื้อหรือหลังจากนั้น?
- มีข้อจำกัดด้านเทคโนโลยี ทักษะทีม หรือโครงสร้างพื้นฐานใดที่กระทบการเลือก broker และวิธีเก็บสถานะ?
